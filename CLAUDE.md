# CLAUDE.md

## Goal
A Godot 4 (GDScript) prototype of a small, story-driven party RPG: a walkable town slice connected to one turn-based tactics fight.

- **Fight question:** "Is setting up and executing a plan in one fight fun?"
- **Milestone 2 question:** "Can we place art in a slightly angled 2D world and connect exploration, story, and the existing fight through reusable systems, with most content changes made in data instead of code?"
- **Milestone 3 question:** "Can the Milestone 2 systems support multiple connected spaces, with new rooms, objects, and dialogue added mostly through data? Does launching the test fight from an in-world arcade cabinet make it feel like part of the game?"
- **Milestone 4 question:** "Does a second character make players care and want to know what happens next? Can characters and places react to story progress mostly through data?" (The second guest, `new_guest`, shown as `???`.)
- **Milestone 5 question:** "Can story progress change the time of day through reusable, data-driven systems? Does returning to a familiar place at night create tension and curiosity?" (The first night: sleep after meeting ???, wake to a bell, the ferry vanishes at the dock, a new letter, sleep, morning.)
- **Milestone 6 question:** "Is a simple solo fight still satisfying when the plan comes from terrain instead of powerful abilities? Do the discoveries afterward give players a clear reason to keep investigating?" (The morning after: through the cellar hatch, Agador fights rats alone, finds a room of old luggage, brings a ribbon to ???, learns about Dockmaster Pell, and the dock office light goes out.)

**Check every feature against those questions.** If it doesn't help answer them, don't build it. Out of scope: Pell as an NPC, the dock office interior, opening the humming case, explaining the luggage, party recruitment, new abilities beyond the cellar fight, interiors for Rooms 2-4, inventory, full opening scene, party following, a second playable character, naming ??? or the sister, explaining the letters, the ferry or Room 4, a real-time clock, repeating days, a calendar, weather, maps or fights beyond the cellar, changes to the arcade fight (`first_fight`: Tide, Volt, Ember, TNT and its look stay as they are), saves, branching choices, quest log, clue journal, cutscene movement beyond simple pacing (no general cutscene system), music, sound effects, final art, leveling, loot, world map, multiple levels, bosses, balance simulators, pinch zoom, and complex layout systems.

## Setup (every session)
Run `tools/setup_godot.sh` before tests (`tools/setup_godot.sh --web` before a web export). It installs the exact Godot version CI uses (read from `.github/workflows/ci.yml`) into `~/.local/bin` only when it is missing, so it is safe to run every time. Add `~/.local/bin` to `PATH` if `godot` is not found.

## Foundation rules
- **Combat state is plain data.** `BattleState`/`Unit` are RefCounted data with no Nodes, separate from scene objects. They're cloneable, and previews run on clones.
- **The rules run headless on that data.** The view sends commands (`Commands.move`, `use_ability`, `wait`, `end_turn`) through `Rules.apply_command(state, cmd)`, which validates them, mutates the state, and returns an ordered event list. The view only animates those events and never decides outcomes.
- **One seeded RNG** lives in `BattleState` (`rng_seed`/`rng_state`, seeded from the encounter). All gameplay randomness must use `state.rand_int()`, never `randf()`/`randi()`. Cosmetic-only randomness in the view (screen shake) is fine.
- **Content is JSON** in `data/`: heroes (incl. display names), enemies, abilities, encounters, terrain and its interactions (`terrain.json` reactions), rule numbers, `settings.json` (developer switches such as `debug_tile_text`), and for the world: `town.json` (shared tile legend, start spot, tuning), `maps/<id>.json` (one per map: rows, npcs, objects, props, exits), `characters.json` (names, colours, sprite/portrait keys), `dialogue.json` (interactions by id; `_buttons` default labels). Prefer changing data over code.
- **Art is referenced by key** through `AssetCatalog` (`scripts/core/asset_catalog.gd`). `data/assets.json` maps keys (`agador.portrait.neutral`, `town.tiles`) to paths; unlisted keys fall back to `res://art/<key>.png`. Never put a file path in code or content. A missing asset logs one warning and shows a placeholder; it never crashes.
- **Story state is plain data too.** `StoryFlags` (named flags, story values such as `time_of_day`, run-once trigger memory; `meets_rule` checks `requires`/`unless`/`time_of_day`), `Dialogue` (picks the first entry whose rule matches, steps lines, applies a line's `then` step when it is left, applies `set_flags`/`set_time`/`start_fight` at the end), `GameSession` (flags, current map/cell/facing, fight in progress; `GameSession.current`), `TownMap` (one map built for a set of flags: walkability, paths, targets, `stand` cells, exits and arrivals, pacers, trigger zones), `Lighting` (a map's preset for the time of day, and its light pools). All headless. No map-specific or story-specific logic in code: exits carry target map, arrival cell and facing; who is where comes from world-state rules.
- **World state is data.** An NPC or object in `data/maps/<id>.json` may list `states`: `{ "requires": [...], "unless": [...], "time_of_day": "night", "priority": n, ...keys }` (any of the rule keys may be left out). Of the matching states the highest `priority` wins (default 0; ties go to the one listed first), and only that one state applies: its keys (`cell`, `facing`, `hidden`, `interaction`, `sprite`, `shape`, `stand`, `pace`, `mood`) replace the base keys. `"hidden": true` removes the thing (no sprite, no blocking, nothing to tap). `WorldState` (`scripts/core/world_state.gd`) resolves it; `TownMap.load_map(id, flags)` applies it on every map load, and `town.gd` re-applies it after each conversation (rebuilding the map behind a short fade only if something on it changed). A character in two places (the second guest in the lobby and the lounge) is listed on both maps with states that show it in one.
- **Time of day is a story value, not a clock.** `time_of_day` (`day`/`night`, start and list in `town.json`) lives in `StoryFlags`, so it survives map changes and fights; direct Fight launches never touch it. Only dialogue data changes it: a line's `"then": { "set_time": "night", ... }` (or an entry's `set_time` at its end). Dialogue entries, NPC/object states and triggers can require it with `"time_of_day"`.
- **Dialogue steps, not cutscenes.** A line's `then` plays after it, before the next line: `set_flags`/`set_time` (applied by the runner when the line is left), `card` (+ `card_time`: a text card over a screen fade; a tap skips it), `place` [x, y] + `facing` (where Agador stands after the fade), `fade_out`/`fade_in` (world object ids fade, `fade_time`; no screen fade when that is all). The dialogue box holds (`busy`) and `town.gd` plays it (`play_step`), rebuilding the map for the new flags/time.
- **Lighting is data.** Each map names a preset (`"lighting": "outdoor"`/`"inn"`) from `town.json` `lighting_presets`, one look per time: `tint` (ground), `tile_tints` (per legend char: darker water, a visible dock), `prop_tint`, `actor_tint` (characters and anything tappable: keep bright), `lit_tint` (things with a `glow`), and `glows` (kind -> stepped light pools `radius`/`steps` or panes `rect`, `blend` `add`/`mix`). Tiles (legend `glow`) and things (`"glow": kind`) name glow kinds. No engine lights: modulate + additive shapes (`town_lighting.gd`), so the web build looks the same everywhere. `light.pool` art replaces the stepped rings if it exists.
- **Trigger zones are data.** A map's `"triggers": [{ "id", "cells", "interaction", "requires", "unless", "time_of_day", "once", "facing" }]`: walking onto a cell stops the walk and starts the interaction when the rule matches; `once` triggers are remembered in `StoryFlags`.
- **Pacing, not cutscenes.** An NPC state with `"pace": [[x, y], ...]` walks that route back and forth (`Pacer`, `scripts/core/pacer.gd`; `TownMap.step_pacer`), pausing `pace_wait` seconds at each point facing its `facing`. Timing is `pace_step_time`/`pace_wait` in `town.json` (overridable per NPC). It pauses during dialogue and while the player walks over to it, never steps onto the player or the player's path (it turns around instead), and tests check that no route cell is a stand cell or arrival and that every target stays reachable with the pacer on any route cell. `"mood": "upset"` draws a mark above the head (art key `mood.<name>`, placeholder otherwise).
- **Screens report, the app decides.** `app.gd` swaps start menu / town / fight. The town screen shows any map and changes maps itself (fade) through exits and dialogue `go_to` steps; it emits `fight_requested(request)`; the fight takes `encounter_id` + `from_town` and emits `fight_finished(won)`, and the player returns to the encounter's `return` spot for that result (`{"won": {"map", "cell", "facing"}, "lost": {...}}`), else to the spot they launched it from. The start screen also shows one button per enabled `shortcuts` entry in `settings.json` (the "Cellar test": a fresh story with those flags, time and spot).
- **Encounters are data.** `encounters.json`: `map` + `legend` (board, any size), `terrain` (overrides merged over `terrain.json` for that fight only, e.g. the cellar's oil `flare`), `objects` (terrain tiles placed by cell, e.g. `cellar_lantern`), `party` (or `heroes`), `enemies`, `seed`, `presentation` (`"style": "pixel"` with `tile_css` and board `tiles` art keys/patterns; none = the arcade look) and `return`. A hero may name a town `character` for its name, colour and sprite. Ability keys `uses`, `source_tile`, `target_surface`, `source_becomes`; unit keys `avoids` (surfaces it won't walk on) and `carries` (an element it brings onto a surface it enters). `BattleState.tile_info/surface_info/reaction` give this fight's rules; never read `terrain.json` directly in rules.
- **One command runs all headless tests** and exits non-zero on failure (see below).
- **CI:** `.github/workflows/ci.yml` runs the tests on every push to `main`, builds a no-threads web export (`tools/build_web.sh`), and publishes it to GitHub Pages. The page has a robots noindex tag.
- **Compatibility renderer**, for reliable mobile browser support.

## Input and layout rules (PC + phone browser)
- Design for a portrait phone first. Larger screens use the extra space (landscape: board left, panel right) without shrinking text.
- **One input model for mouse and touch:** tap or click to select, then tap or click the same thing again to confirm. Nothing may depend on hover or right-click. Long-press or the Info button shows details.
- Touch targets are at least 48 CSS px (`ScreenMetrics` keeps 1 UI unit close to 1 CSS px). The full 10x10 grid stays readable without zooming. Respect safe areas (notch, gesture bar).
- Town: one tap walks to a tile; tapping an NPC/object walks next to it and starts its interaction; tapping an exit walks next to it and fades to its map. In dialogue, one tap finishes the typing, the next advances. Town zoom snaps so each art pixel is whole device pixels (crisp, nearest filtering).
- Input stays separate from combat logic. `board_input.gd` turns pointer input into tap/long-press gestures, and `main.gd` turns gestures into Commands.

## Structure
- `data/*.json`: content and tuning
- `scripts/core/`: fight rules (`battle_state`, `rules`, `commands`, `enemy_ai`, `level_loader`, `game_data`, `unit`) and town/story (`asset_catalog`, `story_flags`, `dialogue`, `game_session`, `town_map`, `world_state`, `pacer`, `lighting`). No Nodes.
- `scripts/view/`: `app.gd` (screen switcher, main scene `scenes/app.tscn`), `start_menu.gd`, fight: `main.gd` (controller, `scenes/main.tscn`), `hud.gd`, `board_view.gd` (arcade and pixel looks), `board_input.gd`; `pixel_art.gd` (placeholders shared by town and the pixel fight: character, rats, lantern); town: `town.gd` (controller, `scenes/town.tscn`), `town_tiles.gd` (TileSet from `town.tiles` or generated), `town_actor.gd` (depth-sorted sprite/placeholder), `town_lighting.gd` (light pools and window panes), `dialogue_box.gd` (`scenes/dialogue_box.tscn`); shared `screen_metrics.gd` (scale, safe areas, DPR)
- `tests/`: `run_tests.gd` (runner), rule/story/town/world-state/night/asset/ui-text suites, `ui_smoke.gd` (fight in phone and desktop layouts), `flow_smoke.gd` (real app on a phone: town -> inn rooms -> arcade fight -> back beside the arcade -> Room 1 key -> the second guest's scene -> the inn afterwards -> the first night: sleep, card, inn and town at night, a night fight, the dock trigger and ferry, the night letter, sleep, morning -> the cellar: hatch, a lost and a won fight, the luggage, ??? and the ribbon, the innkeeper, the dock office light; the Cellar test button), `world_links.gd` (how maps connect: exits, dialogue map changes, fight returns)
- `tools/setup_godot.sh` (install Godot), `tools/build_web.sh`, `export_presets.cfg`: web export

## Conventions
- New interactions: add an object/NPC with an `interaction` id to a map in `data/maps/` and entries under that id in `dialogue.json`. No code.
- New rooms: add `data/maps/<id>.json` and an exit pointing at it (plus one back), or a dialogue line whose `then` has `go_to` + `place` + `facing` (the cellar hatch). Tests check every arrival (exits, `go_to` places, fight returns, shortcuts) is walkable and every target is reachable from every arrival, for every combination of the flags the map's states use. A thing bigger than a tile lists the extra cells it blocks in `footprint`.
- New fights: add an encounter to `encounters.json` and a dialogue entry with `start_fight` + `win_flags` (on an object or a trigger). No code.
- Story reactions: set a flag in a dialogue entry's `set_flags`, then add a `requires` entry at the top of an interaction in `dialogue.json` and/or a `states` rule on an NPC/object. Add `"time_of_day": "night"` to react to the time. No code.
- Time changes: a line's `then` with `set_time` (plus a `card` and `place`). Lighting: edit `lighting_presets` in `town.json`, or a map's `lighting`. Triggers: a map's `triggers`. No code.
- New characters: add them to `characters.json` (name, colour, sprite and portrait keys) and list the keys in `assets.json`. Placeholder portraits show a short name (up to 3 characters, like `???`) in full, else its first letter.
- New placeholder art shapes go in `town_actor.gd` (`ANIMATED` for looping ones); new tile patterns in `town_tiles.gd`.
- New mechanics go in `rules.gd` (with a new event type if needed) and are animated in `BoardView._play_event`.
- Core scripts use `preload` constants, not `class_name`, so the tests run without an editor import.
- Tabs for indentation, typed GDScript where inference works. Small, focused commits. This is a public repo: never commit secrets, keys or personal info.

## Running tests
```sh
tools/setup_godot.sh                                           # once per session: installs Godot if missing
godot --headless --path . --script res://tests/run_tests.gd   # all tests; non-zero exit on failure
```
With a display (`xvfb-run -a godot --path . --script res://tests/run_tests.gd -- --shots=<dir>`) the smoke tests also save screenshots.
Add `test_*` methods to a suite in `tests/` (register new suites in `SUITES`). Build small boards with `make(map, heroes, enemies)` from `test_base.gd`, and assert against values read from `data/`.
